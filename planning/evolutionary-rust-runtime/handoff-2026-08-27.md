## The dirty tree: sub-slice 4b, finished but not committed

Four files: `crates/bittery-client-core/src/runtime/teardown.rs` and `teardown_tests.rs`,
`src/worker-runtime.ts` and `worker-runtime.test.ts`. 851 insertions.

4b makes a wedged Device wipeable. A user reaches for "wipe this device" exactly when the Runtime
can no longer open, and until now that request was refused.

- Core: `ensure_teardown_precondition` requires only `ensure_not_closed()` for Device `Wipe`.
  Account-scope `RemoveAccount` keeps `ensure_open()`.
- Web: the SharedWorker keeps a Runtime whose `open()` threw and forwards an exact `{"type":"wipe"}`
  to it, so the Runtime stays the single destruction authority.

Two independent reviews found two real defects, both fixed, both of the same shape — a request
racing a closing Runtime:

1. `retire()` tested its holder count synchronously, but a wipe only takes its hold after it yields.
   Any other request arriving first closed the Runtime under the live wipe, and the next request
   opened a **second** Runtime over the same storage. Fixed with a `wipesPending` count taken before
   the first `await`.
2. `retire()` then still cleared `runtimeTask` before awaiting the close, so a request arriving
   mid-close built a second Runtime anyway, and `service.close()` resolved with writes outstanding.
   Fixed with a `restartBarrier` installed in `retire()`.
