## What Ticket 48 still owes

### Next slice — the start-up seeding rule

Decision 4. Files: `apps/web/src/lib/storage.ts` (`initializeStorage` and the seeding rule). There is
no `storage.test.ts` today; the slice adds one. `initializeStorage()` is memoised, so the rule
applies per page load.

Why it matters: an abandoned removal leaves no active pointer while the Accounts list and
`secret_key` survive under the login Account id. Start-up currently reads that as a fresh browser and
seeds a synthetic id, so the next log out sweeps an empty Account, reports success, and the real key
material survives behind a screen that says it is gone. This changes the boot path for every session,
so it needs its own tests and its own review rather than riding along with another slice.

### Follow-up slice — the deletion dialog's browser-only escape

After the Server has deleted the Account, a wedged Device refuses `RemoveAccount` forever and the
Secret Key stays in plain `localStorage` for an Account that no longer exists. This is strictly worse
than the log-out case decision 5 was invented for, and it is a regression: the old path never touched
the Runtime, so a wedged Device could previously finish the whole deletion.

`AccountDeletionIncomplete` already structurally satisfies the escape, so the machinery fits. Only
the copy is new, and the existing wording is false here — it says the Account is still on this Device
and on the server, and the server half is no longer true.

## Traps a later slice must not walk into

- **The transitional Web store's Account id is not the Runtime's `AccountId`.** The synthetic
  `bittery_web_account_id` only seeds the *pre-login* active Account; a sign-in mints or reuses a
  different id and points the store at that, so a signed-in user's transitional keys are named by the
  **login** id. The two removal calls name different things and cannot be swapped one for one.
- **Never report success while named data may remain.** This exact defect was found and fixed three
  separate times inside 4c-1, twice after it had supposedly been fixed. The store nulls its active
  pointer before it sweeps values and never rethrows, so a half-finished clear leaves state that
  reads as "nothing to do". The guard is now a type error rather than a check, and a test double that
  had encoded the bug as intended behaviour was flipped.
- **Routing a gesture through the Runtime makes it inherit the Runtime's failure modes.** Twice in
  4c-2 this turned a gesture that always worked into one that could trap the user. Whenever you move
  a path onto the Runtime, ask what happens on a wedged Device before you ask anything else.
- **A retry must not re-resolve the Account.** Once catalog detachment succeeds the catalog no longer
  answers for that Account, and re-resolving can return a **different** one.
- **Convergence can need three attempts, not two.** A platform-namespace failure forbids the Replica
  phase, because the Device catalog lives in that namespace. Retry interfaces must not implement
  "retry once, then report permanent failure".
- **A teardown-fenced request answers `AccountMissing`.** Do not render that as "this Account does
  not exist".
- **`RemoveAccount` and `Wipe` ignore `RequestCancellation`.** A UI `AbortSignal` will not stop a
  teardown.
- **After a `Wipe`, Core closes every subscription while the binding's sink stays open**, so a host
  status observation goes silent with no signal. Reopen observations rather than rendering the
  emptied Device through the old one. Account scope is unaffected; 4c-1 verified this rather than
  assuming it.
- **Retiring a wedged incarnation after an incomplete wipe discards Core's in-memory pending-scope
  tombstone**, so the host, not Core, owns driving that retry.
- **The wedged-Device recovery covers an `open()` that throws, not one that hangs.** A hung `open()`,
  for example an IndexedDB version-change block from another tab, produces no wedged incarnation and
  so no wipe path.
- **`packages/ui` may not import `packages/core`.** That is why the Web UI reaches the lifecycle hub
  through `apps/web/src/lib/*`.
- **Source-text tripwire tests are load-bearing here, and fragile.** `apps/web/src/lib/runtime-session.test.ts`
  is the only guard on several UI contracts, because the package cannot render. Bound each slice to
  its own branch or function; three tripwires in 4c-2 initially sliced to end of file and each
  survived the exact mutation its own comment warned about.
