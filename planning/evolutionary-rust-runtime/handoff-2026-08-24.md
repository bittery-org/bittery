## What the review found

Committed as `75f75fc8` first, so every later slice is reviewable against an honest restore point.

- **Web Sign-in could not succeed at all.** The committed WebAssembly bundle had last been generated
  three commits before `withConfiguredExecutors` existed, so it was absent at runtime. The Worker fell
  back to `withExecutors`, which leaves `auth_client_config` unset, and every `SignIn` answered
  `AuthenticationUnavailable`. What earlier review called an unreachable compatibility shim was the
  only path that ran.
- **A signed-out Account stayed unlocked in memory.** `RuntimeRequest` had no Sign-out or Lock
  variant, so the Web sign-out path cleared only the transitional store while the Worker kept the
  master unlock key and the decrypted Items.
- **The vault sidebar froze after one navigation.** Observation ids were derived from the Account, so
  the layout and every page inside its `Outlet` registered the same one, and both the listener map and
  the Rust observation map replace on insert.
- **A restart showed an empty vault.** A restored Account was `SignedOut`, the Items observation
  answered `AuthenticationRequired`, and the host turned every failure into an empty list. For a
  password manager that reads as data loss.
- **The one boundary the work crossed had no generated contract**, while three neighbouring
  boundaries did.

## Decisions taken this session

Both were maintainer decisions, asked and answered rather than inferred.

1. **The not-yet-ported write kinds are not gated.** After the cutover, update, delete, favorite,
   move, and share still write to the transitional repository and appear to do nothing. Building UI
   that refuses them is throwaway work, because this rebuild ships only once every path is ported, so
   no user meets the gap. Recorded in ticket 22; ticket 28 pulls them over.
2. **The cross-kind Operation outcome contract.** Lookup answers one union tagged on `kind`, because
   response-loss recovery is exactly the caller that does not yet know what happened. Rejections share
   a common core and add only genuinely new per-kind failures, because a single generic code would
   leave the client unable to tell re-authenticate from reload from stop. Items convert before
   Rotation, because Items are what block the Web host. Recorded in ticket 24, which narrowed to the
   Item routes, with ticket 29 created for Rotation.

## Method that produced this

Worth keeping, because most of the real findings came from it rather than from feature work.

- One primary agent owned sequencing, integration, and every commit. Subagents got one bounded slice
  each, with disjoint paths, and never committed.
- Every slice was implemented test-first, and each subagent was asked to show the failing test before
  the fix. Several reported that a test they expected to be stale was in fact a real defect, and the
  reverse.
- Subagent reports were verified independently before committing, not taken at face value. That
  caught a stale protocol validator fixture and a repo-wide formatting failure that the slices' own
  verification had missed.
- Subagents were told which parts of their own ticket to distrust. Ticket 24's rejection list, ticket
  26's dependency direction, and ticket 26's Worker URL indirection were all wrong, and were corrected
  with evidence rather than followed.
- Unresolved maintainer decisions were asked in German and written up in English.
