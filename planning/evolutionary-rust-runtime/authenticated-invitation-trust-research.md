# Authenticated invitation and trust research

Checked 2026-09-23. This is a source inventory for [102](issues/102-authenticated-invitations-and-team-key-trust.md), not a protocol proposal. It does not change ticket readiness or the mandatory policy in [100](issues/100-recipient-key-verification-policy.md) and [101](issues/101-runtime-recipient-key-verification.md).

## Invitation links

**First-party facts.** Proton Pass documents a random share key generated locally, a URL carrying that key in its fragment, encrypted item-key material uploaded to Proton, configurable expiration and view limits, and link revocation. Its help page says anyone obtaining the complete URL can access the shared item while the link remains usable. ([Proton Pass link security](https://proton.me/support/pass-secure-link-security); [launch details](https://proton.me/blog/pass-secure-link-sharing), accessed 2026-09-23.)

**Inference for Bittery.** This is a useful example of keeping a link secret out of the service request and bounding exposure. It is item sharing to a link holder, not authenticated Team membership: the cited flow does not bind acceptance to a Team, inviter authority, intended Account or recipient public key. Expiration, revocation and a view limit bound capability lifetime/use; they do not identify the person who has the link or prevent forwarding. The docs do not define whether failed/concurrent opens consume a view, how acceptance races resolve, or how to recover from a lost response. Ticket102 still needs those exact lifecycle/idempotency rules and the full Server/Team/inviter/recipient transcript binding. A fragment alone only separates a capability from the request in this example; it is not proof of an authenticated identity or membership decision.

## Signed histories, authority and freshness

**First-party facts.** 1Password describes Account Trust Log entries as operations, previous-entry hashes, signer signatures and metadata. Clients verify that the signer key is in the prior World State, the previous-entry reference is valid, and the entry number advances by one. Admin confirmation of a new user is signed, and the admin must already have been authorized and not subsequently removed. The initial trust root is the first account owner. However, the documented model is explicitly trust-on-first-use: a client joining or seeing the log for the first time has no local bookmark and implicitly trusts the server's claim about the latest entry to create one. The page assigns the server responsibility for keeping one sequential shared log; it does not document an independent cross-client fork-detection channel or a freshness bound. ([1Password Account Trust Log security](https://support.1password.com/account-trust-log-security/), accessed 2026-09-23.)

**Protocol evidence, not an adopted design.** The IETF Key Transparency Protocol is an active Internet-Draft (`draft-ietf-keytrans-protocol-05`, July 2026; not an RFC). It requires clients to retain verified tree heads and use consistency proofs for later views. Its security considerations say clients need durable history state; a stateless client gains little over checking a service signature, and going offline longer than a configured log-entry maximum lifetime may miss malicious changes. The companion Architecture draft (`draft-ietf-keytrans-architecture-09`, June 2026) explains that a server can show a forked view unless clients compare views through a trusted auditor, anonymous communication, or peer-to-peer gossip; gossip itself needs adequate connectivity to resist partitioning. ([Protocol draft](https://datatracker.ietf.org/doc/draft-ietf-keytrans-protocol/), §§4, 10–14, 16; [Architecture draft](https://datatracker.ietf.org/doc/draft-ietf-keytrans-architecture/), §§3, 7.)

**Inference for Bittery.** Signatures establish authorization only relative to an already trusted signing key; a signed history alone does not authenticate its first key, prove that a view is current, or prevent a server from isolating devices on different forks. 1Password is a useful example of prior-state signer authorization, but its documented TOFU bootstrap conflicts with102's explicit rejection of server-supplied initial trust. The IETF drafts describe transparency-log mechanisms and tradeoffs, not Team membership governance or Bittery's Vault roles. No cited source chooses Bittery's trust anchor, signer/role rules, anti-rollback/fork mechanism, freshness window, or state-retention obligations.

## Trusted-device transfer and recovery

**First-party facts.** 1Password's QR sign-in pairs a new device with an already linked app/browser through an end-to-end encrypted channel, transfers session information and key material, and requires a confirmation code or prompt. Its support page describes Noise-protected channels and time-bound pairing credentials. Team recovery is instead an authorized-member workflow: an owner, administrator or recovery-permission member initiates recovery; the member receives a new Secret Key and password, and the authorized person completes recovery. The docs recommend at least two members able to recover accounts. ([QR sign-in security](https://support.1password.com/qr-code-security/), published 2024-11-04; [team recovery](https://support.1password.com/recovery/), accessed 2026-09-23.)

**Inference for Bittery.** Pairing demonstrates the dependency on an existing trusted endpoint and explicit user intent; it is not a drop-in contract because it transfers session/key material, while102 requires Runtime-owned trust transfer and forbids exporting Session credentials. The cited recovery workflow demonstrates a separate recovery authority and redundancy practice, but does not specify how a recovered account re-establishes Trust Log state or provide a zero-authorized-recoverer bootstrap. No-trusted-Device recovery therefore remains a product/security decision, not a detail derivable from these sources.

## Decisions still needed for102

- Specify what the invitation secret proves, how first-contact trust binds the canonical Server, Team, inviter authority, intended recipient identity and exact public key, and what the inviter confirms. Decide whether confirmation requires the inviter to be online or supports a retained asynchronous decision.
- Define expiry, cancellation, successful-use linearization, failed and simultaneous acceptance, forwarding/theft consequences, and idempotent retry after an ambiguous response. An owner confirmation alone cannot authenticate a human who obtained a forwarded capability.
- Seal the signed-history governance rules: which existing Team roles may add, remove or rotate signer keys; how authorization changes and key revocation are represented; and how Vault-role permissions remain separate from trust in a Team key.
- Choose how clients retain and transfer verified checkpoints, detect rollback/forks, and bound freshness when offline or after local state loss. Define whether a new Device can inherit trust only from an existing verified Device, and which authenticated evidence can replace that path.
- Choose the fail-closed or reviewed recovery procedure when no trusted Device or authorized recoverer remains, and the explicit onboarding path for existing Teams. This must not silently convert [100's](issues/100-recipient-key-verification-policy.md) manual verification into first-use trust or populate trust from Server/recovery data.

Until these decisions are independently reviewed, 102 remains a product direction rather than an implementable protocol. Existing mandatory recipient verification remains in force; its acceptance still depends on the separate implementation and browser requirements recorded in [101](issues/101-runtime-recipient-key-verification.md).
