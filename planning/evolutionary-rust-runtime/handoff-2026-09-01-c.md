## What step 1 actually does

- `bulkImportItems` is replaced in place by an Operation executor mirroring `createVault`: requires
  `Idempotency-Key`, takes raw bytes through `ApiJsonBytes`, returns `OperationOutcome`. One
  transaction holds the Item set, exactly one `vault_updated`, exactly one bulk audit row, the
  retained outcome and `operation_resolved`. An empty applied batch writes outcome and
  `operation_resolved` only. No parallel route, legacy response type or compatibility writer survives.
- Every refusal reachable from accepted work is a retained semantic rejection. Read-only role →
  `vault_read_only`; no access → `vault_access_denied`; an existing or in-body duplicate identity →
  `item_id_conflict`; bad ciphertext → `invalid_ciphertext`. Rejections write an
  `item_import_rejected` audit row on the **Operation**, never the Vault, matching the sibling
  Operations.
- The Server fingerprint matches the Runtime's `import_items_fingerprint` byte for byte: four
  length-prefixed parts, **path only, no HTTP method** — the one Server fingerprint without a method.
  Two vectors are pinned from the frozen conformance corpus.
- New route `POST /api/v1/vaults/{vaultId}/item-authority-pages` (`getVaultItemAuthorityPage`),
  returning a bare `Vec<ItemResponseDto>` with the next cursor in the `Bittery-Next-Cursor` response
  header, exposed via CORS. The cursor is bound to a digest of the sorted, deduplicated identity set.
- **The stranding fix.** See the next section; this is the most important thing in the diff.

## The defect that cost two review rounds, and how it was closed

Both axes independently found it. A batch the Runtime accepted by **item count** could exceed the
Server's 16 MiB body limit, get a `413`, and — because `runtime/outcome.rs` maps every
non-200/non-`OPERATION_ID_REUSED` status to `SemanticAnswer::Transient` — be retried forever. Sixteen
valid 1 MiB Items were already enough. The same arithmetic broke the authority read from the other
side: `MAX_IMPORT_AUTHORITY_BYTES` is also 16 MiB and accumulates across **all** pages, so paging did
not help, and the response shape is ~433 bytes per Item fatter than the request.

Fix: bound the batch **at Runtime acceptance**, on the exact frozen request bytes, so an unsendable
batch is refused before anything durable exists. Raising the limits instead would have meant ~220 MiB
request bodies and ~220 MiB client buffers.

| Constant | Value |
| --- | --- |
| `SERVER_IMPORT_BODY_BYTES` | 16,777,216 |
| `MAX_IMPORT_AUTHORITY_BYTES` | 16,777,216 |
| `AUTHORITY_ITEM_ENVELOPE_BYTES` | 1,024 (measured worst case 433) |
| `AUTHORITY_PAGE_FRAMING_BYTES` | 1,600 |
| `DERIVED_IMPORT_REQUEST_CEILING` | 16,570,816 |
| `MAX_IMPORT_REQUEST_BYTES` | 15,728,640, leaving 822 KiB slack |

Pinned three ways: two build-time `const assert!`s, a Runtime test with a ">= 512 KiB slack" clause so
it cannot be tuned to the last byte, and a mirrored Server test following the `ITEM_BODY_LIMIT_BYTES`
precedent. The conformance corpus needed **no** regeneration and is byte-unchanged.

## Handover into the Web step, carried from step 1

- **`SizeRejected` must be a per-Item skip, not a per-batch warning.** `use-vault-import.ts` batches by
  count only (`IMPORT_BATCH_SIZE = 200`) and now needs a byte budget too. Once it batches by bytes,
  the only remaining trigger is a single Item that alone exceeds the budget; warning per batch would
  silently drop that Item's siblings and corrupt the final counts and skipped numbers the ticket
  requires preserved.
- **The budget is measured on the serialized encrypted JSON**, exactly what `accept_import_items`
  measures on `body.len()` — not plaintext, not raw ciphertext length.
- **`MAX_IMPORT_REQUEST_BYTES` is `pub(crate)`**, so a Web host must re-type the literal.
  `MAX_IMPORT_ITEMS` already sets that precedent, but record it as a conscious decision and consider a
  drift guard.
