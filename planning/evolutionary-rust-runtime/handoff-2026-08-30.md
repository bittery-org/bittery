## Ticket 28 C contract

C is a **foreground, non-durable Attachment Upload**, not an accepted `Operation`. Its closed public
request contains Account ID, Item ID, bounded decrypted name and content type, declared plaintext
size, and an opaque source-capability ID. The result exposes only the new Attachment ID and
authoritative revision. The host must never provide Runtime incarnation as public caller input.

The deep Rust Attachment module owns the complete flow:

1. Claim a single-use plaintext source capability scoped to actual Runtime incarnation, Account,
   Item, exact request and declared size.
2. Derive Vault/uploader/key authority; encrypt name and content type and stream the bytes in the
   unchanged persisted Attachment format.
3. Obtain the authenticated upload grant with at most one Session renewal.
4. Send exact encrypted bytes through the production binary executor and enforce declared
   plaintext/ciphertext lengths and the Rust SHA-256 digest.
5. Create metadata through the unchanged Server route. Never blindly replay an ambiguous mutation;
   probe authoritative Item/Attachment state instead.
6. Require an exact authoritative effect and one guarded Replica commit before reporting success.
7. Serialize with the existing per-Item writer, create no durable Operation, zeroize owned
   plaintext, and cancel/drain source and binary cleanup before Lock, Sign-out, Remove, Wipe, close,
   failed-open retirement, or Account/incarnation authority can retire.

The production Web source registry owns opaque capability grant/claim/read/close, inclusive bounded
retained identity state, replay and expiry tombstones, failed cleanup retry, Account retirement and
explicit completion, failed-open pending incarnation retirement, and fresh reconstruction. The
Worker reverse RPC must transfer only full owned `ArrayBuffer` views and preserve the existing
plaintext wipe and fail-closed rules. Generated Kotlin, Swift, Runtime protocol, and WASM shapes may
travel with C; native production source registries remain later-host work.

The required C browser acceptance is deliberately narrower than D: one **successful generated
`UploadAttachment`** through production Web composition, Worker, source registry, reverse RPC,
generated real WASM Core, controlled HTTP/storage authority, and production binary executor. It
must observe grant, encrypted PUT, metadata creation, exact guarded reconciliation, source cleanup,
and the closed result. It must not substitute fake Core and must not expand into D's live Server,
SRP/authentication, Move artifact, restart/unlock, or repeated-preparation-failure acceptance.
