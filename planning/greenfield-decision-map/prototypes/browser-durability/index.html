Throwaway decision prototype

What survives when a browser runtime disappears?

This demo tests a narrow question: after Bittery asks browser storage to accept one complete local operation, can a forced Worker termination expose a partial commit, and what can the browser honestly promise about the result?

It can observe transaction atomicity and runtime termination. It cannot simulate power loss, prove an OS disk flush, or predict later origin eviction.

    Cases that decide the promise

    An Account operation, its encrypted object, and its optimistic overlay belong to one transaction. Kill the Worker while it is still issuing writes. Watch for a whole old or whole new state—never a mixture.

    The browser commits, but the runtime dies before the engine hears success. The operation survived, although the caller could only report an indeterminate result until reopening the Replica.

    Transaction completion does not protect an origin from browser policy or a person clearing site data. This scenario removes both stores, including an unsynced operation.

    OPFS exposes a flush attempt, not a stronger documented acknowledgement. Compare termination before flush with a completed flush. This primitive probe is not a transactional SQLite adapter.

    Interpretation rule: one successful run can falsify atomicity if it exposes a partial state. Repeated clean runs cannot prove crash durability, protection from eviction, or parity across other browser engines.
