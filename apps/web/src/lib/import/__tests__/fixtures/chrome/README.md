## Provenance

### `chromium-*.csv` — exporter output asserted by Chromium's own tests

| Field | Value |
| --- | --- |
| Product | Chromium (upstream source, `main`) |
| Version | not a release build; taken from `main` as of 2026-07-29 |
| Platform / OS | POSIX (`\n` records), plus one Windows variant (`\r\n`) |
| Export date | n/a — generated by the exporter's unit tests, not a user export |
| Source | `components/password_manager/core/browser/export/password_csv_writer_unittest.cc` |

Each file is the exact byte string a `PasswordCSVWriter::SerializePasswords`
test asserts, so Chromium's own CI fails if these stop matching what Chrome
writes:

- `chromium-single-password.csv` — `SerializePasswords_SinglePassword`
- `chromium-android-and-web.csv` — `SerializePasswordsWritesNames`
- `chromium-sorted.csv` — `SerializePasswordsIsSorted`
- `chromium-single-password-windows.csv` — the same
  `SerializePasswords_SinglePassword` expectation with `kLineEnding` set to
  `\r\n`, which is what the test itself does under `BUILDFLAG(IS_WIN)`. Note the
  newline **inside** the quoted note is CRLF there too, because the test builds
  the note from the same `kLineEnding`.

Escaping in these files follows
`components/password_manager/core/browser/export/csv_writer.cc`: a field is
quoted only when it contains `\r`, `\n`, `"` or `,`, and an inner `"` is doubled.
The inline synthetic rows in `chrome.test.ts` are built to the same rule
for the cases Chromium's tests do not cover.

### `bitwarden-spec-*.csv` — Chrome exports vendored from Bitwarden's importer suite

| Field | Value |
| --- | --- |
| Product | Chrome (version not recorded upstream), pre-`note`-column export |
| Platform / OS | not recorded upstream |
| Export date | not recorded upstream |
| Source | `bitwarden/clients`, `libs/importer/src/importers/spec-data/chrome-csv/` |
| Original files | `simple-password-data.csv.ts`, `android-data.csv.ts` |

Copied verbatim out of the TypeScript template literals Bitwarden's
`ChromeCsvImporter` spec parses. They are this repository's only evidence for the
four-column `name,url,username,password` layout and for an Android row whose
`name` column is empty, so the parser accepts that layout **only** because these
exist. Values in them were already fake upstream; nothing was changed. Neither
file ends with a trailing newline — that is how the upstream literal ends, and
the parser must tolerate it.

## Accepted header layouts

| Layout | Pinned by |
| --- | --- |
| `name,url,username,password,note` | the `chromium-*` files |
| `name,url,username,password` | the `bitwarden-spec-*` files |

Matching is exact and ordered. A reordered, extra or missing column raises
`csv-unknown-header-variant` and imports nothing. Do not widen this list without
adding a fixture to this directory first.

## Expected losses

Chrome's CSV carries login data only. Everything below is absent from the file
itself, not dropped by us, so no per-item warning is raised for it:

- TOTP secrets
- Passkeys
- Folders / groups (every item lands in one synthetic `Chrome Passwords` vault)
- Favorites (every imported item is `favorite: false`)
- Cards, identities, secure notes, custom fields
- Password history and any timestamps

One shape worth knowing: Chrome writes **one row per affiliated domain**, so a
single saved credential can appear as several rows. Each becomes its own Bittery
item; nothing is deduplicated.

Android credentials keep their `android://<hash>@<package>` URL verbatim. Bittery
cannot open it, but rewriting it to an invented scheme would put a URL in the
vault that the export never contained. When such a row has an empty `name`, the
package name is used as the title.

## Sanitizing applied

None. No file here came from a real vault: the `chromium-*` files are compiled
test expectations and the `bitwarden-spec-*` files were already synthetic
upstream. `biome.json` excludes this directory so the formatter cannot rewrite
byte-sensitive content.

## Known gaps — no authentic user export yet

The issue asks for a sanitized export produced by a real Chrome install,
recording Chrome version, OS and export date. That file does not exist yet, and
these fixtures do not substitute for it. Still unpinned by any authentic export:

- [ ] **A real `chrome://password-manager/settings` export**, with its Chrome
      version, OS and export date recorded above.
- [ ] **A comma, quote or newline inside a real `name` or `note`** — the quoting
      rule is covered synthetically and by Chromium's note test, but not by a
      user-produced file.
- [ ] **Non-ASCII text from a real export** — covered synthetically only.
- [ ] **A `name`-less variant other than the Android row** — the research note
      mentions platform variants that omit `name`; none is accepted, because
      none is pinned here.
- [ ] **Android exports from Chrome on Android** — the two Android rows here
      come from desktop exports of Android-affiliated credentials.

Re-check `password_csv_writer.cc` and re-copy the Bitwarden spec data on
meaningful Chromium releases before widening the accepted layouts.
